결론

조회 12% · 파일 상태 전이 88%. 성능 설계의 중심은 목록 렌더링이 아니라 파일시스템과 DB의 정합성을 지키면서 상태 전이를 싸게 만드는 것입니다.

두 도메인의 차이도 분명합니다

TDB(도면) — 살아 있는 자료. 리비전·반출·검수·분기(병합 필요)를 가집니다.
MDB(데이터북) — 고정 기록. Tag 이력과 설비유형 분류만 있고 리비전·반출·검수가 없습니다.
기존 시스템은 둘을 같은 틀로 묶어 코드가 비대해졌습니다.

04현황 진단 · 구조

반드시 고쳐야 할 3가지

기능의 문제가 아니라 구조의 문제 — 부분 수정으로는 풀리지 않습니다

① 폴더

폴더가 테이블이 아니라 문자열이다

기존 소스 주석 그대로 — “폴더는 실제 테이블이 없는 가상 개념”. documents.source_path 문자열로만 존재합니다.

결과 — 폴더 이름 한 번 바꾸면 수천 건 문자열 UPDATE + 디스크 파일 이동이 함께 일어납니다. 중간에 실패하면 DB와 디스크가 어긋나고, 되돌릴 방법이 없습니다.

② 저장

DB 경로가 곧 디스크 경로이고,
파일명이 메타데이터를 들고 있다

최신/{원본경로}/{도면번호}_Rev00.pdf — 리비전이 오르면 파일 이름이 바뀝니다.

결과 — 승인 1건마다 디스크 rename과 DB UPDATE가 묶여 돌고, 같은 파일이 여러 벌 중복 저장됩니다.

③ 장시간 작업

엑셀·Zip·백업·변환이
요청 스레드에서 동기 실행된다

엑셀 내보내기 17종, Zip 반출, 백업, DWG 변환이 모두 동기 처리입니다.

결과 — 큰 건을 돌리면 화면이 수십 초 멈추고, 그동안 다른 사용자의 조회까지 함께 느려집니다.

06개발 방향성

개발 방향성 — 3원칙

기존 시스템을 기능 100% 보존하면서, 관리성과 성능을 1순위로 재구성합니다

원칙 1

기능을 깎지 않는다

메뉴 9 / 화면 14 / 권한 리프 36 / API 201을 전수 목록으로 고정하고 그대로 재현합니다. 범위 축소는 저희가 아니라 CM 결정 사항입니다.

쓰시던 화면 구성·용어·단축 동작을 그대로 두어, 전환 후 재교육 부담을 없앱니다.

원칙 2

관리성과 성능이 1순위

같은 기능을 고치기 쉬운 구조로 다시 짭니다 — 계약(타입) 1벌 공유, 모듈 규약 통일, 권한·감사는 선언하지 않으면 서버가 뜨지 않게.

성능은 설계가 아니라 측정으로 지킵니다. CI에 성능 기준을 걸어 두어 느려지면 빌드가 실패합니다.

원칙 3

동등성은 증명한다

① 기존 API 201개와 계약 스냅샷 대조
② 기존 화면 요소(버튼·라벨) 체크리스트 자동 대조
③ 신·구 서버에 같은 요청을 보내 응답을 직접 비교(섀도 비교 2주)

데이터 이행은 건수와 sha256 전수 일치로 확인합니다. 눈 검사로 대체하지 않습니다.

07개발 방향성 · 업무 규칙

바꾸지 않는 것 — 승계하는 업무 규칙

기존 시스템에서 CM이 확정해 둔 규칙은 그대로 코드로 고정했습니다

규칙내용신규 시스템에서의 구현
삭제 기능이 없다어떤 경우에도 줄을 지우지 않는다. 보관함(삭제·폐기)으로 옮기고 복구 가능상태만 전이 · 폐기 보관함은 완전 삭제 없음
자동 병합하지 않는다A·B 업체 동시 수정 시 분기 리비전으로 각각 보관하고 ‘병합 필요’ 부여리비전 상태 머신을 순수 함수로 분리 — 단위 테스트 28건
리비전 정수는 승인돼야 오른다반려는 정수를 소모하지 않고 글자(a·b·c)로 이력에 남는다동일 규칙 그대로. 반려하면 그 반출은 다시 미반납
감사 로그는 고칠 수 없다수정·삭제 불가DB 권한·트리거 수준에서 차단 (애플리케이션이 아니라)
권한 트리에 없는 기능은 개방2026-08-12 CM 확정 사항리프 36개 그대로. 트리에 없는 키를 보내면 거부
‘최신’ 폴더는 그대로 남는다“시스템을 그만 써도 최신 폴더만 가져가면 쓸 수 있어야 한다”야간 배치가 하드링크로 재구성 — 디스크 추가 사용 없음
중복 반출을 막지 않는다경고만 한다 — 막으면 분기 흐름이 성립하지 않는다경고 + 중복반출 현황 화면
위 규칙은 설계 문서가 아니라 실행되는 테스트로 고정되어 있습니다. 규칙을 어기는 코드가 들어오면 빌드가 실패합니다.

09개발 방향성 · 정정

정정 — PDF 뷰어는 ‘포크’가 아닙니다

인수인계 문서(S-21)의 위험 평가를 코드 대조로 확인한 결과

문서상 기술

“PDF.js 원본 viewer.mjs·pdf.worker.mjs를 직접 수정한 8,400줄 포크”
→ 보안 패치를 따라갈 수 없는 자산으로 분류, 재작성 대상

실제 확인 결과

원본 수정은 2곳(하이라이트 표시 방식)뿐. 8,400줄은 전부 덧붙인 별도 모듈 17개입니다.
→ 재작성 대상이 아니라 그대로 이식하는 자산. 이식 완료 상태입니다.

대상실제 수정량조치
web/viewer.mjs · build/pdf.mjs0줄그대로 사용
build/pdf.worker.mjs2곳패치로 고정해 업스트림 갱신 추적 가능
dms-*.js 17개 (8,400줄)별도 모듈전부 이식 완료 — 도형·측정·스탬프·마크업 동작 확인
마크업(즐겨찾기)은 기존에 파일로 저장하던 것을 DB로 옮겼습니다 — 사용자가 보는 동작은 같고, 백업·이관 대상이 하나 줄었습니다. PDF.js 버전은 최신 계열(6.3)로 올려 두었습니다.

11개발 방향성 · 해법

구조 문제 3가지 — 어떻게 풀었나

핵심은 하나 — 파일을 움직이지 않는다. 디스크를 건드리지 않으니 어긋날 일이 없습니다

작업기존 (경로 기반)신규 (blob 기반)효과
폴더 이름 변경 (하위 500건)문자열 UPDATE 500건 + 디스크 이동 500건줄 1개 UPDATE수십 초 → 1ms 미만
리비전 승인 1건디스크 rename 2~3회 + UPDATE줄 UPDATE만디스크 작업 0
자료 이동디스크 이동 + UPDATE줄 UPDATE만디스크 작업 0
같은 파일 중복그대로 중복 저장내용이 같으면 한 벌만 저장용량 절감
작업 중간 실패DB와 디스크가 어긋남 — 수동 복구트랜잭션 되감기로 끝정합성 보장
엑셀·Zip·백업화면이 멈춘 채 대기즉시 응답 + 진행률 표시다른 사용자 영향 없음
‘최신’ 폴더는 그대로 유지됩니다. 야간 배치가 blob에서 하드링크로 트리를 다시 만들어 두므로, 기존처럼 탐색기에서 열어 복사해 가실 수 있고 디스크를 추가로 쓰지 않습니다.
